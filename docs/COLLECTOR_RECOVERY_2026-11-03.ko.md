# SCA Monitor 수집 복구 및 NVD 검증 기록

작업 시작일: 2026-11-03, Asia/Seoul. 이 문서의 초기 관찰과 중간 중단 기록은 최종 결과와 구분한다.

## 범위와 보존

SCA Monitor의 실제 소스 수집 실패를 조사하고 운영 수집을 복구했다. ARTEX 연동용 서비스 인증이나 exploit 실행 기능은 이번 변경에 포함하지 않았다. 실제 운영 채팅·진단·발견·보고서·결과 UI의 전체 흐름을 검증했다는 의미도 아니다.

작업 전 로컬/운영 체크아웃은 `d2674ed`였다. 운영은 `ai-assistant` 서버의 사용자 systemd 서비스다. 확인한 kubectl 컨텍스트에서 SCA Monitor 이름의 Deployment·Service·CronJob은 없었으며 다른 클러스터 전체를 조사한 것은 아니다.

원래 계정·설정·자산·스냅샷·자격증명·권고를 초기화하지 않았다. 기존 ZIP, 백업과 원본 소스도 삭제하지 않았다. 운영 원본·소스·전환/실행 증거는 다음 서버 경로에 보관했다.

```text
/data/psyche/Projects/sca-monitor/releases/collector-recovery-20261103T081010Z/
```

초기 온라인 백업은 제한시간을 넘겨 검증되지 않은 사본으로 남겼다. 별도 일관 읽기 스냅샷으로 만든 `database-before-consistent.sqlite3`는 819,576,832바이트이며 `quick_check=ok`와 테이블 조회를 확인했다. 이 초기 백업에는 권고 236,333행, 서비스 15행, dependency snapshot 13행, 사용자 1행, session 1행, push credential 2행이 있었다. 권고 행 수는 고유 CVE 수가 아니다.

## 확인한 실패 원인과 변경

| 관찰 | 증거와 수정 |
|---|---|
| OSV·OpenSSF·NVD가 각각 21,600초 후 종료 | 소스 상태의 timeout 메시지와 실제 systemd 로그에서 확인했다. 처리량과 중복 작업을 줄이는 방향으로 수정했으며 제한시간만 늘리는 방식으로 성공 처리하지 않았다. |
| KEV의 SQLite 잠금 오류 | 실제 실패 로그에 `sqlite3.OperationalError: database is locked`가 있었다. 수집 쓰기를 실제 트랜잭션 구간에서 조정하고 짧은 배치로 커밋한다. |
| KEV/NVD가 CVE별로 전체 권고를 읽음 | 별칭 색인의 CVE 키로 관련 행만 조회한다. 운영 EXPLAIN에서 primary-key/별칭 색인 사용을 확인했다. |
| NVD 수정 목록에서 원문을 받은 뒤 같은 CVE를 개별 재조회 | 수정 구간의 페이지에 포함된 전체 CVE 원문을 직접 저장한다. 완료된 일 단위 구간별로 커서를 저장하고, 불완전 페이지·중복·전송 실패·부분 처리 때는 완료 커서를 전진시키지 않는다. |
| NVD discovery 페이지의 요청 간격/재시도 부족, 429 | 페이지와 구간 사이에 같은 요청 클라이언트를 사용한다. 운영에서는 6.2초 간격을 사용했고 429/일시적 서버·전송 오류에 제한된 재시도를 적용했다. `Retry-After`도 존중한다. 영구 권한 거부는 재시도하지 않는다. |
| 같은 제품의 CPE 버전 조건마다 원문/상품 행을 반복 갱신 | 기존 레코드 식별자 규칙을 유지하면서 제품별로 조건을 묶고, 원래 NVD JSON의 configurations를 보존한다. CVE 보강은 정규 CVE ID로 한 번 수행한다. |
| OSV/OpenSSF가 MAL 레코드의 출처를 반복 변경 | OSV 파서의 기존 MAL→OpenSSF 규칙을 유지한다. 중복 미러 수집으로 같은 행과 별칭을 매번 재작성하지 않는다. |
| 전체 dump 완료 전에 개별 OSV 레코드가 성공 상태를 기록 | 배치 입력에서는 개별 성공 상태 기록을 억제하고 dump 전체 결과를 기록한다. 부분 실패가 최근 전체 성공처럼 표시되지 않게 한다. |
| HDD 커밋 I/O 대기 | `/data`는 회전식 장치, 사용자 홈은 SSD였다. 스택 샘플 3회가 배치 commit 대기를 가리켰다. 합성 500행/FULL 시험에서 HDD 100행 배치는 약 0.795초, SSD는 약 0.0251초였다. 이 수치는 합성 시험이며 전체 운영 수집 지연을 뜻하지 않는다. |
| 대량 원문의 전송 지연 | 공식 API가 gzip을 지원함을 확인했다. gzip/일반 응답을 모두 처리하고 잘린 gzip도 재시도한다. 실제 실행에 HTTP 상태·인코딩·요청 구간·페이지/저장 수를 기록한다. |
| 갱신이 독립적인 NVD/KEV 보강 정보를 덮어쓸 가능성 | 원천 JSON과 보강 정보를 구분해 보존하고, 후속 NVD/OSV 갱신으로 이미 확보한 KEV 근거를 지우지 않게 했다. |

성공 판정에 systemd 상태나 planner식 완료 선언만 사용하지 않았다. 실제 GET·페이지 본문·저장·완료 커서·별도 원문 조회를 대조한다. 빈 결과는 유효한 API 응답에서 totalResults=0이고 전체 배열이 빈 경우에만 정상적인 빈 구간으로 인정한다.

## 저장소 전환과 백업

DB와 WAL의 원본 HDD 사본을 보존한 뒤 SQLite backup API로 SSD 복제본을 만들었다. 31개 테이블의 건수가 일치하고, 계정·서비스·스냅샷·자격증명 등 보호 대상 14개 테이블의 내용도 전환 전후 동일함을 확인했다. 이 전환 시점의 권고는 250,388행이었다.

```text
기존 논리 경로:
/data/psyche/Projects/sca-monitor/.data/sca-monitor.sqlite3

현재 실제 DB:
/home/psyche/.local/share/sca-monitor/sca-monitor.sqlite3

보존한 HDD DB:
/data/psyche/Projects/sca-monitor/.data/sca-monitor.before-ssd-20261103.sqlite3
```

기존 논리 경로는 SSD DB를 가리키는 symlink다. 코드의 DB 경로 해석과 실제 수집 프로세스의 DB/WAL 파일 descriptor가 SSD를 사용하는 것을 확인했다. 기존 환경 파일과 인증 설정은 변경하지 않았다. 전환 중 SCA API와 관련 타이머를 잠시 멈췄으며 API·기존 project/repository 타이머는 원래 활성 상태로 복구했다. 수집 타이머도 전체 정상 주기 검증 뒤 원래의 6시간 주기로 복구했다.

WAL은 로컬 파일시스템에서 사용하며 `synchronous=FULL`을 유지한다. 수집 연결은 제한된 캐시와 100행 배치를 사용하고 체크포인트 간격을 조정한다. NORMAL/OFF로 내구성을 낮추지 않았다. [SQLite WAL 문서](https://www.sqlite.org/wal.html)의 커밋 동기화와 체크포인트 구분에 따른 설정이다.

기존 `scripts/backup_database.py`는 본체 파일만 복사했으므로 WAL 모드의 최신 커밋을 보장하지 못했다. 온라인 SQLite backup API, private/고유 파일명, quick_check로 보완했다. `scripts/verify_backup_restore.py`로 별도 사본의 읽기/스키마 복원도 검증한다. raw 파일 복사나 symlink만 보관한 파일 백업을 최신 DB의 일관된 백업으로 취급하지 않는다.

중간에 HDD commit이 오래 걸려 systemd 정지 유예를 넘긴 NVD 시도는 SIGKILL로 끝났다. 이 실행은 성공으로 세지 않았다. 완료 커서·기존 DB/WAL·중간 이벤트를 남기고, 소유 수집 프로세스가 모두 종료된 것을 확인한 뒤 그 작업의 남은 lease만 복구했다. 재개는 저장된 마지막 완료 커서부터 수행했다.

추가 운영 백업은 HDD 대상에서 600초 관찰 한도를 넘겼으므로 미검증으로 보존했다. 이 사본을 성공한 백업으로 세지 않았다. 별도 SSD 위치에서 기존 온라인 백업 명령을 다시 실행해 3,742,400,512바이트의 일관된 사본과 `quick_check=ok`를 확인했다(약 37.6초). 기존 복원 검증기를 별도 임시 사본에 실행해 migration 22/22 및 서비스·수집 상태·알림 조회를 확인했다(백업부터 복원 검증까지 약 43.85초). 원본과 두 위치의 기존 사본은 삭제하지 않았다. 이 사본은 해당 백업 시작 시점의 snapshot이며 이후 수집 완료 시점의 최신성은 별도 원문 대조 결과로 판단한다.

NVD의 실제 주간 재수집 중 원천 데이터가 갱신돼 페이지 사이 totalResults가 달라지는 경우도 관찰했다. 이 실행은 `partial`로 종료했고 완료 커서는 2026-10-23에 유지됐다. 이미 저장한 자료는 삭제하지 않았다. 이후 기본 완료 구간을 1일로 줄이고, 원천 목록의 건수/중복 변화에 대해서만 같은 구간을 최대 3회 재조회하도록 보완했다. 지속적인 변화·형식 오류·권한 거부를 성공으로 바꾸지 않는다. 재조회로 안정되는 경우와 끝까지 변하는 경우를 실제 localhost HTTP/CLI에서 각각 검증했다.

## 검증 방법

- Python 3.12에서 전체 회귀 352개가 통과했다. 로컬 임시 DB와 실제 localhost HTTP 서버를 사용한다. 운영 Python 3.10은 소스 compile 및 실제 수집으로 별도 관찰했다.
- 검증 사례에는 gzip/일반 JSON, 전송 잘림, 429/503 재시도, 403 비재시도, 불완전/빈 페이지, 실제 취소 후 재개, 완료 커서 유지, 다중 CPE 조건/별칭 연계, MAL 미러 중복, 독립 KEV 근거 보존과 열린 WAL의 온라인 백업·복원을 포함한다.
- 실제 NVD 누락 변경분을 완료 구간별로 수집하고, 이어서 기존 `sca-monitor-source-sync.service` 전체 주기를 실행한다. source 상태·반환 수·저장 수·terminal 결과를 확인한다.
- 완료 후 공식 NVD의 최근 수정/신규 구간을 별도로 GET하고, 수집 DB에서 각 CVE의 전체 JSON hash가 일치하는지 확인한다. source modified 시각과 수집 시각을 혼동하지 않는다.
- 초기 백업과 현재 DB를 비교해 보호 데이터 및 권고·영향·이력·알림·감사·저장소 결과의 기존 ID 보존을 확인한다. quick_check와 foreign_key_check도 수행한다.

| 독립 대조 범위(KST) | 공식 레코드 | 전체 원문 일치 | 누락/불일치 |

두 범위는 겹칠 수 있으므로 709개의 서로 다른 CVE라고 해석하지 않는다. 초기 보존 검증 스크립트가 일부 테이블에 단일 `id`가 있다고 가정해 원문 수신 이후 중단됐다. 기존 원문/기록은 보존했고 실제 테이블 기본키를 사용하는 비교로 수정해 최종 검증을 실행했다. 이 중단은 수집 성공이나 보존 검증 통과로 세지 않았다.

API는 최종 코드로 재시작한 뒤 로컬 `/ready` 200, database=ok를 확인했다. 이 readiness의 필수 소스는 기존 3개이므로 위의 5개 소스 전체 조회를 별도로 수행했다. `sca-monitor-api.service`는 running이고 source/project/repository worker timer는 active 상태이며 주기에 따라 waiting/running으로 전환된다. 마지막 source 서비스가 inactive/dead인 것은 성공한 oneshot의 정상 상태다. 이전 실패한 임시 복구 unit의 로그/상태는 보존했다. 로컬·운영의 변경한 소스/테스트 8개 SHA-256이 배포 manifest와 일치한다. 변경 사항은 로컬 및 운영에 적용했으며 Git commit/push는 하지 않았다.

2026-11-03 20:03:55 KST 최종 검증이 종료 코드 0으로 완료됐다. 초기 백업 대비 보호 대상 14개 테이블의 기존 행 누락/변경은 모두 0이었다. 권고·영향·이력·알림·감사·저장소 실행/컴포넌트/엣지 8개 테이블에서도 기존 기본키 누락이 모두 0이었다. 현재 운영 DB의 `quick_check=ok`, `foreign_key_check` 위반 0건, WAL 및 `synchronous=2(FULL)`을 확인했다.

권고는 초기 236,333행에서 최종 364,500행으로 증가했고 그중 NVD 출처 행은 124,540행이다. 이 수치는 고유 CVE 수가 아니다. 출처 정규화 및 미러 갱신으로 소스별 분류가 이동할 수 있으므로 특정 출처 행 수의 감소를 기존 ID 삭제와 혼동하지 않는다. 마지막 NVD 원천 수정 시각의 최대값은 2026-11-03 19:17:20.437 KST였으며, 완료 커서 19:49:52 KST는 수집한 조회 구간의 끝이다.

초기 백업까지 중복 검사하던 별도 읽기 전용 검증은 중지했으며 성공으로 세지 않았다(`verification-redundant-stopped.json`). 기존 데이터 비교와 공식 전체 응답 대조를 유지한 별도 명시적 운영 DB 검사가 위 최종 결과다.

운영 증거는 위 복구 디렉터리의 `collection-completed.json`, `verification-final.json`, `verification-*/pages/`, `storage-cutover.json`, `online-backup-restore-ssd.json`, `deployed-code-manifest.json`에 있다. 원문 및 보존 검증 스크립트 `verify-recovery.py`, `verify-recovery-main.py`도 함께 보관했다. 최종 스크립트는 이미 실제 GET으로 받은 전체 페이지를 재사용했으며 `official_pages_reused_from`으로 원래 요청 증거 경로를 남겼다. 이 재검사 출력의 `method=GET`은 원래 수신 방법을 가리키며 새 네트워크 요청을 뜻하지 않는다. 최종 무결성 검사는 `main` 운영 DB를 명시했고 초기 백업은 작업 전 별도로 `quick_check=ok`를 확인했다.

## 복구 시 준수할 점

코드 롤백을 우선하며 DB 스키마를 초기화하지 않는다. SSD 전환 후 새 데이터가 생겼으므로 과거 HDD DB나 초기 백업을 현재 DB 위에 바로 덮어쓰지 않는다. 저장소를 되돌려야 하면 현재 SSD DB를 일관되게 복제하고 검증한 뒤 경로를 전환한다. 이전 소스의 raw 파일 백업으로 되돌릴 경우 WAL 누락 문제가 재발하므로 온라인 백업 수정은 유지한다.

이 검증은 지정 구간의 실제 수집·저장과 근거 보존에 한정된다. 과거 NVD 전체 초기 적재의 완전성, 공급자의 공개 데이터 자체의 완전성, CPE 조건의 범용 자동 판정, 특정 대상의 exploitability, 인증 후 운영 UI 전체 및 ARTEX native 분석 흐름은 이 작업에서 검증하지 않았다. `/ready`의 HTTP 200도 전체 소스의 최신성 보증으로 사용하지 않는다.
