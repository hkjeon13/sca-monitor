# SCA Monitor 화면/API 재설계 초안

작성일: 2026-10-27 (KST)

## 1. 제품의 중심 질문

1. **보안 정보:** OSV, GHSA, OpenSSF, CISA KEV, NVD에서 무엇이 보고되었는가?
2. **프로젝트:** 내가 관리하는 프로젝트와 서비스는 무엇인가?
3. **영향:** 그 보안 정보가 내 프로젝트의 실제 패키지 또는 실행 환경과 맞는가?
4. **조치:** 지금 무엇을 처리해야 하며, 알림은 전달되었는가?

`보안 정보(advisory/source record)`와 `영향(finding)`은 다른 단위다. 하나의 보안 정보가 여러 프로젝트·서비스·환경에 영향을 줄 수 있고, 어떤 보안 정보는 등록된 자산에 영향을 주지 않는다. 모든 화면에서 이 둘의 건수를 분리해 표시한다.

현재 웹 콘솔의 어두운 사이드바, 상단 요약, 카드형 패널은 유지한다. 좁은 필드를 한 줄에 몰아넣지 않고 기본 검색 1개와 고급 필터 접기 영역을 사용한다.

## 2. 공통 탐색 구조

| 메뉴 | 주된 질문 | 화면 |
|---|---|---|
| Overview | 지금 내 프로젝트에 무슨 일이 있는가? | 전체/프로젝트 전환이 가능한 대시보드 |
| 프로젝트 | 무엇을 감시하고 누가 관리하는가? | 목록, 등록 마법사, 프로젝트 상세 |
| 보안 정보 탐색 | 각 소스에 어떤 취약점/악성 패키지가 있는가? | 통합 검색, 5개 소스 탭, 상세 |
| 영향 및 조치 | 등록 자산에 실제로 무엇이 해당하는가? | 영향 목록, 근거, 담당자, 상태 |
| 알림 | 어떤 규칙으로 누구에게 전달되었는가? | 프로젝트별 규칙/채널, 발송 이력 |
| 연동 | 패키지와 환경 정보를 어떻게 보내는가? | endpoint, push, SBOM 예시 |
| 운영 상태 | 수집·매칭·알림 작업이 정상인가? | 소스 신선도, 실패, 마지막 성공, 작업 상태 |

상단에는 프로젝트 선택기(`내 전체 프로젝트` 또는 하나의 프로젝트), 조회 시각, 계정 메뉴를 둔다. 프로젝트를 바꾸면 Overview·영향·알림의 범위가 함께 바뀌고, 보안 정보 탐색은 기본적으로 전역 공개 데이터에 머문다. 검색 결과에는 `내 프로젝트 영향 있음` 필터를 제공한다.

각 화면은 **한 문장 설명 → 핵심 숫자 → 검색/필터 → 결과 → 상세 패널** 순서로 표시한다. `i` 버튼은 클릭과 키보드로 열리며 지표의 정의, 집계 범위, 갱신 시각을 보여준다. 툴팁을 닫을 때는 다시 클릭하거나 Esc를 누른다.

## 3. 보안 정보 검색 및 조회

### 화면

- `통합`, `OSV`, `GHSA`, `OpenSSF`, `CISA KEV`, `NVD` 탭을 둔다.
- 통합 탭은 CVE/GHSA/OSV 별칭으로 같은 이슈를 연결한 **정규화 결과**를 보여준다. 소스 탭은 원본 소스 기록을 보여준다. 합쳐진 기록에서도 각 원본의 ID와 링크를 잃지 않는다.
- 기본 검색: CVE/GHSA/OSV/MAL ID, 패키지명, 제품명, 키워드.
- 고급 필터: 소스, 생태계, 패키지, 심각도, KEV, 악성 패키지, 공개/수정일, 내 프로젝트 영향 여부. NVD·KEV 탭에는 제품/CPE 필터를 별도로 둔다.
- 결과 행: 제목, 대표 ID와 별칭, 소스 배지, 심각도, 해당 패키지/제품, 수정일, `내 프로젝트 영향 N건`.
- 상세: 소스별 원문 요약, 영향 버전과 수정 버전, CVSS/KEV 근거, 출처 링크, 마지막 동기화, 연결된 프로젝트 영향.
- 상단에 `저장된 실제 건수`, `검색 결과 건수`, `마지막 성공 수집`, `수집 상태`를 표시한다. `전체 공개 CVE`라는 표현은 사용하지 않는다. 소스가 지연·실패한 경우 목록 위에 경고를 고정한다.

### API 초안

| 메서드/경로 | 용도 |
|---|---|
| `GET /api/v2/intel/sources` | 소스별 실제 저장 건수, 수집 범위, 마지막 성공, 실패, 지연 상태 |
| `GET /api/v2/intel/advisories` | 별칭으로 연결한 통합 보안 정보 검색 |
| `GET /api/v2/intel/advisories/{canonical_id}` | 통합 상세와 연결된 원본 기록 |
| `GET /api/v2/intel/records?source=OSV` | 소스별 원본 기록 검색. `source`는 다섯 값 중 하나로 제한 |
| `GET /api/v2/intel/records/{source}/{record_id}` | 소스 원본 상세와 통합 기록 연결 |

검색 파라미터는 `q`, `id`, `ecosystem`, `package`, `product`, `severity`, `kev`, `malicious`, `published_from`, `modified_from`, `project_id`, `cursor`, `page_size`로 시작한다. `page_size` 기본 25, 최대 100. 응답에는 `items`, `total`, `next_cursor`, `as_of`, `source_freshness`, `coverage_note`를 넣는다. 기존의 고정 `LIMIT 200`을 전체 목록처럼 보이게 하지 않는다. 검색은 로컬 색인 기준이며, 외부 API 즉시 조회 기능을 추가하더라도 결과를 `실시간 조회`로 따로 표시한다.

소스의 역할은 구분한다. OSV·GHSA는 패키지/버전 매칭의 주된 근거, OpenSSF는 보고된 악성 패키지, CISA KEV는 실제 악용 이력에 따른 우선순위, NVD는 CVE/CVSS/CPE 보강 자료다. 소스별 데이터 모델이 달라 같은 필터가 모두에게 적용되는 것처럼 보이지 않게 한다.

## 4. 계정별 프로젝트 등록 및 관리

### 데이터 모델

- `user`: 검증된 로그인 주체의 안정적인 ID와 표시 이름. 이메일은 변경될 수 있으므로 유일한 영구 식별자로 사용하지 않는다.
- `project`: ID, 이름, slug, 설명, 상태, 기본 알림 정책, 생성자.
- `project_membership`: 프로젝트, 사용자, 역할(`owner`, `maintainer`, `viewer`), 초대/활성 상태.
- `monitored_target`: 프로젝트 안의 서비스/애플리케이션과 환경(`prod`, `stage`, `dev` 등). 기존 `services`를 이 모델에 연결한다.
- `inventory_snapshot`: 특정 대상의 패키지 목록과 수집 시각. 패키지 좌표(PURL/생태계/이름/버전)를 필수로 하고 OS·컨테이너·런타임/CPE 정보는 제공될 때만 저장한다.

프로젝트 소유자는 구성원·연동·알림 규칙을 관리한다. Maintainer는 자산과 영향의 조치 상태를 관리하고, Viewer는 조회만 한다. `accepted_risk` 승인에는 별도 보안 승인 권한을 요구한다. 모든 API는 서버에서 프로젝트 멤버십을 검사한다. 다른 프로젝트 ID를 넣어도 데이터가 노출되지 않아야 한다.

### 화면

- **프로젝트 목록:** 내 프로젝트 카드, 환경 수, 최신 인벤토리 시각, 열린 영향, 수집 이상. 이름/상태 검색.
- **등록 마법사:** (1) 이름과 설명 → (2) 첫 서비스·환경 → (3) 수집 방식(endpoint/push/SBOM) → (4) 알림 채널 → (5) 검증. 빈 프로젝트 생성도 허용한다.
- **프로젝트 상세:** `개요 / 서비스·환경 / 패키지·인벤토리 / 영향 / 알림 / 구성원·설정` 탭. 각 자산의 마지막 성공 수집과 버전 확인 가능 여부를 보여준다.
- **환경 탐색:** OS/이미지/런타임/CPE가 있으면 표시하고, 없으면 `정보 미제공`으로 표시한다. 단순히 환경이 `prod`라는 이유로 OS 취약점 매칭을 확정하지 않는다.

### API 초안

| 메서드/경로 | 용도 |
|---|---|
| `GET /api/v2/me` | 로그인 주체와 접근 가능한 프로젝트, 권한 |
| `GET /api/v2/projects` · `POST /api/v2/projects` | 내 프로젝트 목록·등록 |
| `GET /api/v2/projects/{id}` · `PATCH /api/v2/projects/{id}` | 프로젝트 상세·수정 |
| `GET /api/v2/projects/{id}/members` · `POST /api/v2/projects/{id}/members` | 구성원 조회·초대 |
| `GET /api/v2/projects/{id}/targets` · `POST /api/v2/projects/{id}/targets` | 서비스/환경 조회·등록 |
| `GET /api/v2/projects/{id}/inventory` | 최신 인벤토리와 신선도 |
| `POST /api/v2/projects/{id}/targets/{target_id}/snapshots` | 대상에 한정된 패키지/SBOM 전송 |

쓰기 요청은 검증 오류를 필드별로 반환하고, snapshot push는 프로젝트·대상에 범위가 묶인 자격 증명과 멱등 키를 사용한다. 삭제 대신 프로젝트 `archive`를 우선 제공한다. 기존 데이터의 프로젝트 귀속이 확정되기 전에는 자동 이동하지 않는다.

## 5. 영향 탐색 및 알림

### 판정

`finding`은 `프로젝트 + 대상 서비스/환경 + 패키지 또는 환경 구성요소 + 정규화 보안 정보`의 매칭 결과다. 결과를 다음처럼 구분한다.

| 판정 | 뜻 | 기본 알림 |
|---|---|---|
| `confirmed` | 확인된 버전이 취약 범위에 들어감 | 위험도 규칙에 따라 발송 |
| `potential` | 제품/CPE 등 정황은 있으나 버전 또는 근거가 부족함 | 별도 검토 대기 |
| `unknown` | 인벤토리나 보안 정보가 오래돼 현재 영향 여부를 판단할 수 없음 | 수집 이상 알림 |
| `not_affected` | 검증된 근거로 영향 없음 | 발송하지 않음 |

패키지 매칭에는 생태계·정규화 이름·버전 범위를 사용한다. NVD/CISA의 제품·CPE 정보만으로 패키지 취약 버전을 단정하지 않는다. 결과 상세에는 **왜 매칭됐는지**, 사용 중 버전, 영향 범위, 수정 버전, 프로젝트/환경, snapshot 시각, 출처를 함께 제시한다.

### 화면/API

- 영향 화면 기본값은 `내 전체 프로젝트의 미해결 confirmed`; `potential`과 `unknown`은 별도 탭/건수로 표시한다.
- 필터는 프로젝트, 서비스/환경, 위험도, 상태, KEV/악성, 발견일. 기본 검색과 고급 필터를 나누고 적용·초기화 버튼을 겹치지 않게 둔다.
- 상세 패널에서 근거 → 권장 조치 → 담당자/상태 → 알림 이력 순으로 읽는다.
- 알림은 프로젝트별 규칙(신규 Critical/High, KEV, 악성 패키지, 재발, SLA 초과, 수집 지연)을 설정한다. 같은 finding·원인에 대한 중복 발송을 억제하고 전송 성공/실패/재시도를 기록한다. 초기 채널은 기존 Slack/Webhook을 사용한다.

| 메서드/경로 | 용도 |
|---|---|
| `GET /api/v2/findings?project_id=...` | 권한 내 프로젝트의 영향 목록·필터·페이지 이동 |
| `GET /api/v2/findings/{id}` | 매칭 근거, 조치, 이력, 알림 |
| `PATCH /api/v2/findings/{id}` | 상태·담당자·사유 변경(감사 기록) |
| `GET /api/v2/projects/{id}/alert-rules` · `PUT /api/v2/projects/{id}/alert-rules` | 알림 기준 |
| `GET /api/v2/projects/{id}/alert-events` | 발송/실패/재시도 이력 |

## 6. Overview 설계

**범위 선택:** `내 전체 프로젝트` 또는 한 프로젝트. 전체 범위는 사용자가 접근 가능한 프로젝트만 합산한다. URL에도 선택 범위를 넣어 새로고침과 공유 시 같은 화면을 유지한다.

1. 상단 상태 줄: 프로젝트 범위, 마지막 분석 시각, 인벤토리 신선도, 보안 정보 수집 신선도. 소스가 지연되면 숫자 위에 경고.
2. KPI 카드: 감시 프로젝트/대상, 미해결 confirmed, 신규 confirmed(7일), Critical/High, KEV/악성 관련, 수집 확인 필요. `i`에서 집계 기준을 설명.
3. **지금 조치할 항목:** 위험도·KEV·운영환경·기한을 고려한 우선 목록. `potential`은 별도 표식.
4. **프로젝트별 위험:** 열린 영향, 최근 증가/감소, 수집 상태를 프로젝트 카드로 비교. 프로젝트 하나를 선택했을 때는 서비스/환경별 카드로 바뀜.
5. **최근 보안 정보:** 최근 7일에 수집된 전역 이슈와 `내 프로젝트 영향` 여부를 분리해 보여줌. `최근 공개`와 `최근 수집` 날짜를 혼동하지 않음.
6. **추세:** 30일 신규/해결 건수. 데이터 수집 중단 구간에는 그래프에 결측 구간을 표시.
7. **운영 상태:** 5개 소스의 마지막 성공/실패, 인벤토리 지연, 알림 전송 상태. 상세 운영 진단은 펼침 영역으로 둠.

`GET /api/v2/overview?project_id={optional}&window=7d`는 `scope`, `counts`, `urgent_findings`, `project_risk`, `recent_advisories`, `trend`, `coverage`, `as_of`를 반환한다. 모든 건수에 `unit`(`projects`, `targets`, `findings`, `unique_advisories`)을 명시한다. 오래된 데이터에서 `0건`을 안전하다는 의미로 표시하지 않는다.

## 7. 인증, 호환성, 전환 순서

현재 서버는 인증이 비활성화돼 있고, 기존 스키마에는 계정·프로젝트·멤버십이 없다. **계정별 프로젝트 기능 공개 전에 인증과 API 권한 검사를 먼저 완료해야 한다.** Cloudflare Access를 로그인 경계로 선택한다면 백엔드가 전달받은 Access JWT의 서명·issuer·audience를 검증하고, 그 주체를 내부 사용자/프로젝트 멤버십에 매핑한다. 프런트엔드에서 메뉴를 숨기는 것만으로 접근을 통제하지 않는다.

1. 소스 수집 작업과 신선도 복구, 실제 저장 건수/범위 노출. 실패한 수집은 `완료`로 표시하지 않음.
2. 로그인 주체·프로젝트·멤버십 모델 도입. 기존 15개 서비스의 소유 프로젝트를 검토한 뒤 **복사/연결 → 검증 → 전환**. 기존 DB와 v1 API는 전환 검증 동안 보존.
3. v2 보안 정보 검색 및 프로젝트 등록 화면. 검색 결과 페이지 이동과 원본/통합 구분을 검증.
4. 프로젝트 범위의 인벤토리·영향 판정·알림 규칙. 기존 영향의 프로젝트 귀속을 검증.
5. 새 Overview와 반응형 화면, 클릭 가능한 `i` 설명, 키보드 접근성. 실제 데이터와 빈/오류/지연 상태로 화면 검증.

완료 기준: 서로 다른 두 계정의 프로젝트가 API·화면에서 섞이지 않고, 5개 소스의 검색/상세/페이지 이동이 동작하며, 보안 정보·영향·프로젝트 건수가 명확히 구분되고, 수집 지연이 Overview에서 숨겨지지 않는다.
