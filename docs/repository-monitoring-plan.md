# 저장소 기반 프로젝트 모니터링 구현 계획

상태: 2026-10-28 저장소 연결·암호화 자격 증명·1차 리포트·의존성 그래프·OpenRouter 보조·사용자 요청 KVM 심층 분석을 구현했다. 아래 내용은 목표 설계를 포함한다. 현재 지원 범위, 실제 API 및 운영 제약은 [저장소 분석 운영](repository-analysis-operations.md)을 기준으로 확인한다. 웹훅·private registry·다른 이미지 플랫폼 등은 후속 확장이다.

## 사용자 흐름

1. 프로젝트에 GitHub/GitLab 저장소 URL, 브랜치 또는 태그, 선택적 하위 경로를 입력한다.
2. 비공개 저장소는 별도 자격 증명 보관함에서 연결 정보를 만들고 프로젝트에 연결한다. 저장소 URL에 토큰을 넣지 않는다.
3. 저장소의 특정 commit SHA를 기준으로 실행 없는 1차 분석을 수행하고 리포트를 제공한다. 이미지가 분석 대상이면 digest·플랫폼도 고정한다.
4. 발견한 패키지·취약점·설치 행위 후보와 확인하지 못한 영역을 근거와 함께 보여준다.
5. 사용자가 리포트의 **심층 분석 요청** 버튼으로 요청한 경우에만 별도 격리 워커에서 빌드·설치·실행 분석을 수행한다.
6. 직접·전이 의존성 및 OS/런타임 패키지를 환경별로 확인하고 모니터링한다. 1차 결과와 심층 분석에서 추가로 확인된 결과를 구분한다.
7. 저장소 변경 시 1차 분석을 갱신한다. 취약점 데이터가 갱신되면 기존 인벤토리를 재매칭하므로 매번 빌드하지 않는다. 예약·웹훅 갱신이 심층 실행을 자동으로 시작하지 않는다.

기존 프로젝트·서비스·환경·인벤토리 기록은 유지한다. 저장소 연결은 프로젝트에 추가하는 입력 방식이다.

## 1차 리포트 → 사용자 요청 심층 분석

### 1차 분석: 대상 프로젝트 코드를 실행하지 않는 기본 경로

- manifest·lockfile·설치 참조 파일을 정적 파서로 분석한다.
- Dockerfile·CI·셸 스크립트·애플리케이션 코드에서 설치·다운로드·외부 스크립트 실행 후보를 찾는다. LLM 사용이 설정된 경우 파일 간 호출 관계와 동적 명령 구성의 해석을 보조한다.
- 접근 가능한 베이스/완성 이미지와 기존 SBOM을 읽기 전용 분석 워커에서 조사한다. 이미지 안의 프로그램은 실행하지 않는다. 실제 이미지나 인증 정보에 접근할 수 없으면 이미지 내부 패키지는 미확인으로 표시한다.
- 설치, 빌드, `setup.py` 실행, 패키지 매니저의 실행 가능한 메타데이터 훅, 앱 구동은 1차 작업에 포함하지 않는다. 외부 스크립트를 발견해도 실행하지 않는다.

리포트에는 다음 항목을 둔다.

| 항목 | 표시 내용 |
| --- | --- |
| 분석 기준 | commit SHA, 이미지 digest·플랫폼, 모듈·환경, 수집기/규칙 버전, 분석 시각 |
| 확인된 구성 | 패키지·exact version, 근거가 있는 직접/전이 관계, 실제 패키지 식별자와 일치한 취약점 |
| 설치 행위 후보 | 파일·행·호출 경로·해석 근거. LLM 추정과 실행 관찰을 구분하고 의도적 은닉/악성 여부를 단정하지 않음 |
| 미확인 영역 | 동적으로 결정되는 버전·설치 대상, 접근 불가 이미지, 외부 스크립트, 실행 조건 등 |
| 수집 범위 | 조사한/실패한 파일·이미지 및 관계 완전성. 발견된 취약점 0건을 안전 판정으로 바꾸지 않음 |
| 다음 행동 | 미확인 영역별 심층 분석으로 확인 가능한 내용과 **심층 분석 요청** 버튼 |

‘발견 위치’(`repository`, `base_image`, `build`, `runtime`)와 ‘의존 관계’(직접, 전이, 관계 미확인)는 별도 축으로 저장한다. 베이스 이미지에서 발견했다고 자동으로 전이 의존성으로 분류하지 않는다.

### 심층 분석: 사용자가 요청하는 실행 경로

리포트에서 분석 대상·프로파일·최대 실행 시간·허용 외부 통신 범위를 명시하고 요청한다. 프로젝트 owner/maintainer 또는 관리자만 요청·취소할 수 있고 viewer는 결과만 조회한다. 요청 API에서도 같은 권한을 검사한다.

요청은 원본 리포트 ID와 commit SHA·이미지 digest·플랫폼을 고정한 별도 비동기 작업으로 생성한다. 중복 클릭은 idempotency key로 같은 작업을 반환한다. 최신 브랜치나 변경된 이미지 태그로 분석 대상을 몰래 교체하지 않는다. 사용자가 새 버전을 원하면 새 1차 리포트부터 생성한다.

1. 모니터 서버는 요청·권한·실행 프로파일과 작업 상태를 관리한다.
2. 별도 분석 워커가 작업별 일회용 VM 등 격리 환경을 준비한다. VM 내부 컨테이너 사용은 가능하되 일반 컨테이너만을 유일한 격리 경계로 두지 않는 구성을 우선 검토한다.
3. 필요한 설치·빌드·선택한 실행 시나리오를 수행하며 패키지 인벤토리, SBOM, 프로세스·다운로드·파일 변경의 증거를 수집한다. 빌드 단계와 최종 이미지, 실행 중 추가된 구성을 구분한다.
4. CPU·메모리·디스크·시간·통신을 제한하고 운영 DB·서버 디렉터리·Docker 소켓·운영 자격 증명을 분석 대상에 노출하지 않는다. 필요한 private registry 접근은 해당 작업 범위의 제한된 자격 증명 전달 경로를 따로 설계한다.
5. 결과와 마스킹된 증거를 별도 영속 저장소에 보존·검증한 뒤 해당 작업의 임시 실행 환경을 종료한다. 모니터 서버의 DB나 사용자 저장소를 정리 대상으로 삼지 않는다.

화면 진행 상태는 `대기 → 환경 준비 → 빌드/실행 관찰 → 리포트 생성 → 완료`로 표시하고, 부분 완료·실패·취소를 별도 상태로 둔다. 취소/시간 초과 시 확보한 결과와 미완료 범위를 남긴다. 네트워크 정책으로 설치가 차단되면 ‘설치 시도 발견·실제 설치 미확인’으로 보고한다. 관찰 시나리오에서 실행되지 않은 경로는 미검증 상태로 유지한다.

심층 리포트에는 **추가 발견 패키지·새 취약점·확인된 유입 경로·설치 시도·해소된/남은 미확인 항목**을 1차 결과와 비교해 보여준다. 1차 리포트는 수정하지 않고 보존한다. 부분 실패한 심층 분석으로 기존 인벤토리를 빈 목록으로 덮어쓰거나 기존 영향을 자동 해결하지 않는다. 결과를 인벤토리에 반영할 때에도 대상 commit·이미지·환경과 수집 완전성을 유지한다.

## 다양한 파일명·경로·형식 탐지

요구사항은 모든 프로젝트가 비정형이라는 전제가 아니라, 이름·위치·형식이 다를 가능성에 대응하는 것이다. 파일명만으로 의존성 파일을 확정하지 않는다.

| 사례 | 탐지 및 해석 |
| --- | --- |
| `requirements.txt`, `requirements.dev.txt`, `requirements/base.txt` | 알려진 파일명 패턴과 requirements 문법으로 후보 탐지. Dockerfile·CI·Makefile·스크립트의 `pip install -r PATH` 참조를 근거로 우선 확정 |
| 이름이 전혀 다른 `deps/backend-prod.list` | 설치 명령의 파일 참조 추적. 내용 분석만으로 발견하면 후보로 남기고 분석 범위 검토 화면에 표시 |
| requirements의 `-r`·`--requirement` | 포함 파일을 재귀 추적. 순환·중복 참조를 감지하고 저장소 경로 경계를 검증 |
| `-c`·`--constraint` | 버전 제약으로 적용. 제약 파일에만 등장한 패키지를 설치 패키지로 간주하지 않음 |
| `pyproject.toml` | `project.dependencies`, optional dependencies, dependency groups, Poetry 설정 등 지원하는 구조를 파서로 읽음. 임의의 TOML을 의존성 파일로 확정하지 않음 |
| `setup.cfg`, `setup.py` | 정적 메타데이터 우선. 동적으로 계산되는 부분은 미해결로 표시하고 빌드 환경의 수집 결과로 보완 |
| 모노레포 | 하위 경로별 manifest·lockfile·설치 명령을 모듈로 묶고 workspace 관계를 보존 |
| 다른 생태계 | manifest/lockfile 탐지·파싱을 어댑터로 확장. npm/pnpm/Yarn, Maven/Gradle, Go 등은 별도 지원표 관리 |

개발·테스트·운영·optional·platform 조건은 별도 속성으로 저장한다. 선언에만 있고 버전이 확정되지 않은 항목과 실제 빌드·설치 결과를 구분한다. 저장소 정보만으로 운영 배포 상태를 확정하지 않는다.

LLM은 설치 파일·모듈·명령 후보와 파일 간 연결을 설명하고 코드에 숨겨진 설치 가능성을 탐지하는 보조 단계로 사용한다. 지원되는 manifest가 있는 프로젝트에서도 설치 행위 분석을 수행할 수 있다. 출력에 파일 경로·행·근거·확신도를 요구하고 구조화된 스키마로 검증한다. 저장소 내용은 분석 데이터로 취급하며 코드에 포함된 지시문으로 작업 권한·실행 프로파일을 변경하지 않는다. 최종 패키지명·버전·간선은 파서, 패키지 매니저, SBOM 근거로 확인한다. 미해결 후보는 1차 리포트와 심층 분석 검토 목록에 남긴다.

LLM 연동은 별도 설정 단계로 둔다. 비공개 소스의 전송 범위와 모델 제공자를 명시하고 자격 증명·키·비밀 파일은 입력에서 제외한다. 이 설계 단계에서는 외부 모델에 저장소를 전송하지 않는다.

## 전이 의존성 수집과 계층 표시

수집 경로는 다음 순서로 구성한다. 지원 여부와 완전성은 수집기별로 표시한다.

1. **lockfile + manifest**: 실제 고정 버전 및 지원되는 관계를 파싱하고 루트 직접 의존성을 구분한다. 평면 lockfile처럼 관계 정보가 부족하면 그래프 완전성을 낮춰 표시한다.
2. **패키지 매니저 해석 결과**: 해당 환경의 의존성 그래프를 수집한다. Node의 설치 트리, Maven/Gradle 해석 결과 등 생태계별 어댑터를 둔다. Python은 설치 목록만으로 원래 직접 의존성·설치 의도를 복원할 수 없으므로 선언·환경 마커·설치 메타데이터를 함께 사용한다.
3. **CI/빌드에서 생성한 CycloneDX SBOM**: exact version, component, dependency edge를 받아 동일한 내부 그래프로 변환한다. 그래프가 없는 SBOM은 패키지 목록으로 수용하되 관계를 추측하지 않는다.
4. **배포 산출물·실행 환경 보완**: 이미지/환경 SBOM에서 OS·런타임·포함 라이브러리를 더한다. 패키지 발견과 부모 관계의 확인 상태를 분리한다.

저장소 스캔 서버에서 임의의 설치·빌드 스크립트를 바로 실행하지 않는다. 사용자 CI에서 이미 생성한 해석 결과·SBOM은 1차 분석의 입력으로 수용할 수 있다. 서비스가 새로 설치·빌드·실행하는 동적 해석은 사용자가 요청한 심층 분석에 한정하고 격리 워커에서 수행한다. 설치 훅·빌드 메타데이터 단계도 실행 가능 코드로 취급한다.

### 저장 모델

- `repository_connections`: 프로젝트, provider, URL, ref, subpath, credential 참조, 마지막 분석 commit.
- `repository_credentials`: 프로젝트 접근 범위, 암호화된 username/secret, 키 버전, nonce, 암호화 인증 태그. API에는 상태와 표시용 이름만 반환.
- `repository_scan_runs`: 분석 모드(`preliminary`/`deep`), 원본 리포트 참조, 요청자, idempotency key, commit SHA, 이미지 digest·플랫폼, 환경/모듈, 실행 프로파일·제한, 실행 상태, 수집기 버전, 시간, 오류, 완전성.
- `repository_scan_reports`: 분석 ID, 원본 1차 리포트 ID, 확인된 구성·취약점·설치 행위 후보·미확인 영역·수집 범위·증거 참조. 리포트는 버전별로 보존하고 심층 결과 비교를 제공.
- `dependency_components`: 스냅샷 내 패키지 식별자, 생태계, 이름, exact version, purl/qualifier, declared range, 확인 상태.
- `dependency_edges`: 동일 스냅샷·모듈·환경의 parent → child 관계, scope, platform/optional 조건, 근거 참조.
- `dependency_evidence`: 파일 경로·행·수집기·빌드/산출물 식별자·관찰 시각.

패키지와 간선을 분리한 그래프를 저장한다. 동일 패키지가 여러 경로에 나타나거나 직접·전이 의존성 역할을 동시에 가질 수 있다. 버전·플랫폼·해석 문맥이 다르면 별도 component로 유지한다. 기존 `direct_dependency`, `dependency_path`는 이전 데이터 호환에 사용하며, 하나의 경로 필드만으로 다중 부모를 표현하지 않는다.

화면은 `프로젝트 → 모듈/환경 → 직접 의존성 → 전이 의존성`으로 펼친다. 자식은 펼칠 때 제한된 개수씩 조회한다. 순환 참조는 현재 경로의 방문 집합으로 감지하여 표시한다. 관계 미확인 패키지는 별도 그룹에 표시한다.

```text
backend / prod
├─ web-framework@1.0.0       직접
│  └─ common-util@3.0.0     전이 · 취약점 1건
└─ persistence@3.1.0        직접
   └─ common-util@3.0.0     전이 · 같은 패키지의 다른 유입 경로
```

트리에는 유입 경로를 보존하지만 KPI는 동일 환경·스냅샷의 component 식별자를 기준으로 중복 집계하지 않는다. 취약점 상세에 모든 유입 경로와 어느 상위 직접 의존성을 갱신해야 하는지 보여준다. 상위 버전 변경으로 해결되는지는 실제 재해석 결과로 검증한다.

## 비공개 저장소 자격 증명

HTTPS 저장소 URL과 별도 credential ID를 사용한다. username/secret은 인증 암호화(AES-256-GCM 등)로 보관하고, 암호화 키는 DB·저장소와 분리한 서버 비밀 설정 또는 KMS에서 관리한다. 키 버전 기반 교체 절차를 둔다. 화면에서 기존 secret 원문을 다시 조회하지 않는다.

프로젝트 권한을 적용하고 저장소·레지스트리에 필요한 읽기 범위로 제한한다. credential은 clone/API 호출 시에만 복호화하며 URL·프로세스 인자·로그·오류·LLM 입력에 원문을 남기지 않는다. private package registry 자격 증명은 저장소 자격 증명과 구분해 연결한다. GitHub App/GitLab 접근 토큰 지원을 고려하되 최종 provider별 권한표를 구현 전에 확인한다.

GitLab Self-Managed는 provider host를 명시적으로 등록한다. 저장소 조회와 리다이렉트에 목적지 검증·시간/크기 제한을 적용하고 임의 서버 접근 경로로 사용되지 않도록 한다.

## API·화면 초안

| API | 목적 |
| --- | --- |
| `POST/GET /api/v2/projects/{id}/repositories` | 저장소 연결 및 상태 목록 |
| `POST/PATCH /api/v2/projects/{id}/repository-credentials` | 자격 증명 등록·교체. 원문 GET 없음 |
| `POST /api/v2/projects/{id}/repositories/{rid}/scans` | 실행 없는 1차 분석 시작, `202` + scan ID. 심층 실행으로 자동 전환하지 않음 |
| `GET /api/v2/projects/{id}/repository-scans/{scan_id}` | 단계·진행·근거·미해결 파일·완전성 조회 |
| `GET /api/v2/projects/{id}/repository-scans/{scan_id}/report` | 보존된 리포트 및 원본 1차 리포트와의 비교 조회 |
| `POST /api/v2/projects/{id}/repository-scans/{scan_id}/deep-analysis` | 사용자 요청 기반 심층 작업 생성. 고정 대상·실행 프로파일·idempotency key 검증, `202` + 작업 ID |
| `POST /api/v2/projects/{id}/repository-scans/{scan_id}/cancel` | 권한 있는 사용자가 해당 작업 취소 요청. 기존 리포트·확보된 증거 보존 |
| `GET /api/v2/projects/{id}/dependency-roots` | 모듈·환경별 직접 의존성, keyset cursor |
| `GET /api/v2/projects/{id}/dependency-components/{cid}/children` | 스냅샷 범위의 자식 간선, keyset cursor |
| `GET /api/v2/projects/{id}/dependency-components/{cid}/paths` | 유입 경로를 제한·페이지 처리하여 조회 |
| `POST /api/v2/projects/{id}/targets/{tid}/sboms` | CI/산출물 CycloneDX 업로드와 구조 검증 |

프로젝트 상세에 `저장소 / 분석 결과 / 의존성 트리 / 영향 / 자격 증명`을 둔다. 분석 결과는 1차 리포트, 심층 분석 요청·진행, 비교 리포트로 구성한다. 기존 수동 전송·endpoint 방식도 유지한다. `확정 버전`, `선언 범위`, `관계 미확인`, `수집 일부 실패`를 구분해 완전 수집으로 오인하지 않도록 한다.

## 단계와 완료 기준

1. **탐지 기반**: Python 파일명 변형·TOML·포함/제약 파일·모노레포 fixture로 탐지/파서 검증. 설치 참조 없는 후보와 실제 입력 구분.
2. **저장소 및 비밀 관리**: GitHub/GitLab 연결·읽기 권한·암호화·교체·권한 분리·오류 비밀 마스킹 검증. 기존 데이터 백업 후 추가형 migration 적용.
3. **수집/그래프**: 고정 commit 분석, lockfile/해석 결과/SBOM 수용, 다중 부모·다중 버전·순환·부분 그래프·platform 조건 검증. 취약점 매칭은 직접·전이 패키지 모두 수행.
4. **1차 리포트와 화면**: 파일 탐지 검토, 수집 범위·미확인 영역, 지연 로딩 트리, 유입 경로, 중복 없는 KPI, 예약/웹훅 1차 분석과 취약점 갱신 재매칭. 1차 작업이 설치·빌드·앱 실행을 호출하지 않는지 검증.
5. **LLM 보조**: 파일 탐지·설치 행위 후보의 근거 추출과 검토 UX. 지원 형식 내부의 숨겨진 설치, 비정형 fixture, 오탐, 미탐, 비밀 제외 및 제공자 설정 검증.
6. **사용자 요청 심층 분석**: 요청/취소 권한, 대상 고정, 중복 클릭 방지, 격리 워커, 자원·통신 제한, 실행 관찰, 부분 결과 보존과 비교 리포트 검증. 요청이 없는 예약·웹훅 작업에서 심층 실행이 시작되지 않아야 함.
